# Architecture

Status: ACTIVE in Module 3.

## Gate

### Hard Constraints
* **Zero Out-of-Pocket Budget:** Must run with zero software licensing or subscription fees.
* **Deterministic Evaluation:** Identical applicant data must yield identical eligibility results every run.
* **Inspectability:** Code must be fully readable and auditable by a single developer without opaque proprietary middleware.
* **Timing:** Must evaluate applicant eligibility in under 2.0 seconds per the EARS acceptance criterion in `FEATURES.md` (F-02).

### Options Considered
* **Hand-built option (Build):** Vanilla HTML5, CSS3, and JavaScript running client-side with browser `localStorage`.
* **Existing-service option (Buy):** Embedded third-party form/database service (Airtable or Typeform).
* **AI-assisted build (Delegate):** Full AI-generated framework application (React/Next.js scaffold generated by an autonomous coding agent).

### Scoring Anchors
* **Cost to start:** 1 = >$100 setup fees; 3 = paid tiers required after free trial; 5 = $0, completely free.
* **Cost to maintain:** 1 = monthly recurring SaaS/hosting bills; 3 = usage-tiered costs; 5 = zero recurring cost.
* **Time to working:** 1 = >12 hours setup/debugging; 3 = 4–6 hours; 5 = <2 hours to working state.
* **Inspectability:** 1 = closed-source binary or vendor-hosted black box; 3 = complex multi-layered generated code; 5 = plain single-file readable script.
* **Switching cost:** 1 = vendor lock-in with proprietary export schemas; 3 = moderate refactor required; 5 = clean decoupling, easily swapped.
* **Fit to spec:** 1 = cannot meet <2.0s latency or deterministic criteria; 3 = partial fit with external latency; 5 = exact match to EARS acceptance statement.

### Weighted Comparison Matrix
Weights assigned prior to scoring (1 to 5 scale; 5 = most favorable).

|---|:---:|:---:|:---:|:---:|

### Sensitivity Check
If Inspectability were de-weighted from 4 down to 1, assuming inspection was delegated entirely to an external reviewer, the Hand-built score drops from 108 to 93, while Existing-service drops from 65 to 59, and AI-assisted drops from 76 to 70. Hand-built remains dominant because zero cost to start, zero maintenance cost, and direct fit to the sub-second EARS latency constraint outscore the overhead of third-party platforms.

## ADR-001

### Title and date:
ADR-001: Client-Side Vanilla JavaScript and LocalStorage for Candidate Knockout Intake (2026-09-17)

### Status:
Accepted

### Door / concrete acquisition and execution choice:
Build — Hand-built implementation using native HTML5, vanilla JavaScript, and browser `localStorage` running in a local browser environment.

### Context:
`FEATURES.md` defines feature F-02 (Deterministic Operational Knockout Gate), requiring the system to evaluate four strict candidate constraints (graduation date window, degree program, U.S. work authorization, and relocation readiness) in under 2.0 seconds. The project has zero budget, runs locally within a GitHub Codespace via Live Server, and requires complete inspectability so the author can directly audit every line of business logic without third-party dependencies.

### Decision:
Build the candidate knockout intake form and list view directly using semantic HTML5, vanilla CSS, and client-side JavaScript adhering strictly to the load-save-render cycle with browser `localStorage`, rejecting external UI frameworks and hosted SaaS form builders.

### Consequences and revisit trigger:
* **Positive consequences:** 
  * Execution latency is under 50ms, easily beating the 2.0-second EARS acceptance limit.
  * Zero out-of-pocket cost and zero external dependencies or API keys.
  * 100% inspectable and transparent code logic for grading and verification.
* **Negative consequences (what it fails to do):** 
  * Fails to persist candidate data across different devices or browsers because `localStorage` is isolated to the local client.
  * Does not support concurrent multi-user recruiter workflows.
* **Revisit trigger:** Revisit this decision in Module 4 when a shared backend database and authentication layer are introduced to support multi-user persistence.
